## Global constraints

- Canonical User roles/routes and legacy resident compatibility stay intact.
- Daily periods use Asia/Manila calendar days. One unresolved request of each type per ticket; no same-day repeat even after completion.
- User notes: 5/minute/ticket; staff: 20/minute/ticket. Account communication limits: User 20/10 minutes, staff 100/10 minutes. Identical same-author/ticket/visibility notes are suppressed for 60 seconds. All configurable.
- One appeal per dismissal, including archives, no deadline; required explanation, existing evidence only. Admin decision only, accepted appeal and reopening saved atomically.
- Explicit acknowledgement and public response/completion. Viewing, normal notes and status/assignment changes never silently complete requests.
- Operator feature deferred. No normal seeding, provisioning, migration, staging or commit.

## Interfaces

Ticket responses retain the existing shape and add:
- `requests`: records with `_id`, `type` (`follow_up`, `progress_update`, `appeal`), `message`, `state` (`pending`, `acknowledged`, `completed`), `createdAt`, `acknowledgedAt`, `completedAt`, `responseText`, `responseNote`, `decision` (`accepted`, `rejected`) and `decisionReason` where applicable. Staff viewing/history fields are filtered for Users.
- `requestEligibility`: keyed by request type, each `{allowed, reason, nextAllowedAt}`. Present for Users; UI uses this server result.
- `reversal`: Admin-only `{options: [status], legacy: boolean}`.
- `statusHistory`: Admin-only append-only events with `from`, `to`, `kind`, `reason`, `changedBy`, `createdAt`, old completion/archive fields and referenced previous event where known.

Endpoints under the existing ticket router:
- `GET /api/tickets/requests?type=&state=&search=&page=&limit=` (Admin/Employee): `{items, total, page, pages, counts:{outstanding,unread}}`. Each item has request fields plus `ticketId`, `title`, `ticketStatus`, `isArchived`, `requester:{_id,firstName,lastName}` and `read`. Counts reflect the full authorized scope, independent of page/filter. Default page size 10; allowed max 50.
- `POST /api/tickets/:id/requests` (User): `{type,message}`; returns updated role-filtered ticket.
- `PATCH /api/tickets/:id/requests/:requestId` (staff): `{action:'view'|'acknowledge'|'respond'|'decide', text?, decision?, status?}`. Respond requires public `text`; decide requires `decision`, public `text`, and `status` for acceptance. Returns updated ticket.
- `POST /api/tickets/:id/revert` (Admin): `{status,reason}`; returns updated ticket.
- `GET /api/tickets/my-tickets?archived=dismissed` returns only the owner's archived Dismissed reports. Existing default remains active reports.

All mutations preserve existing `{message}` errors; 429 additionally includes `retryAfter` seconds, `nextAllowedAt`, and the Retry-After header. Request ineligibility/status races use 409, invalid input 400, and unauthorized/inaccessible new request resources use 403/404 as appropriate without foreign ticket details.

## Review focus

- Reassignment/deactivation between reading a request and writing a response must deny without exposing content or adding a note.
- Concurrent same-day requests or appeal decisions must yield one persistent action and one public response/history event.
- New status rules must close the ordinary API bypass while retaining previously supported forward actions and no-op timestamp behavior.
- Reopening must not revive inactive assignees or overwrite concurrent notes/priority/link changes; old event timestamps stay auditable.
- User list/detail/mutation/inbox projections and late frontend responses must not disclose internal history or another owner's records.
